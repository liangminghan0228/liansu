# 连溯 · 10 分钟面试讲稿

> 目标岗位：Agent 开发工程师。讲法提示用「」，正文是要点，不用背，按结构讲。
> 口诀：**真源唯一、索引可重建；事实保鲜、只增不改；便宜门控、贵在刀刃；图最后上、增益可测。**

---

## 0:00–0:40 一句话定位

「我做了一个本地长期记忆系统，叫连溯。解决的问题很具体：Agent 每次会话都从零开始，反复问同样的个人信息和偏好；而记忆散落在各平台配置里，不可迁移、不可审计、不可重建。」

「所以我把记忆收敛成一个本地 MCP server：**以 Markdown vault 为唯一真源，以 MCP 为唯一接口，全自动抽取**。WorkBuddy 和 Codex 都能接。」

一句话价值：**让 Agent 跨会话记住你，且记忆可审计、可迁移、可重建。**

---

## 0:40–3:00 设计一：真源唯一 + 索引可重建

「记忆系统最容易踩的坑是**多真源**——向量库一份、图库一份、文档一份，最后对不上。我的第一原则是：只有 `journal/` 是权威，其余全是派生。」

- **真源**：`journal/YYYY-MM.md`，append-only，按时间分片。多设备靠 append-only 天然规避冲突。
- **派生**：向量（sqlite-vec）、BM25、双时态图、entities/topics/brief 视图，**全部可 `rebuild`**。
- **验证方式**：删掉整个索引目 + 视图目录，一条 `liansu rebuild --verify` 完全恢复，且重建前后 TopK 结果一致。

「这里我做了个工程判断：索引删除后不影响真源，所以索引可以随便重建、随便换 embedding 模型——这让系统敢迭代。」

> 讲法：如果面试官问「为什么不直接用现成的记忆库」，答：现成方案多是「记忆即索引」，我坚持真源与索引分离，是为了可审计、可迁移、可重建，这是个人长期记忆最需要的三个属性。

---

## 3:00–5:30 设计二：双时态（回答「现在是否成立」）

「普通记忆系统存的是『事实』，但事实有保质期。『求职目标城市北京/西安未定』和『定了北京』是同一个 predicate，旧信息会污染回答。」

我的做法：
1. 每条 fact 带 `valid_from` / `valid_to`，`valid_to=null` 表示当前成立。
2. **不原地改旧行**——这是 append-only 铁律。改成追加一条 `supersede` 事件（记录 `old_id + new_id + 时间`），重放时计算失效状态。
3. 检索时**时效过滤**：`valid_to <= now` 的事实不进结果。

「这里踩过一个坑：最初方案写『给旧行打 valid_to』，落地时发现这破坏了 append-only。改成事件流后，真源纯追加、时效仍可表达，还能 `git diff` 审计每一次记忆变更。」

口诀：**事实保鲜，只增不改。**

---

## 5:30–7:00 设计三：provider 解耦 + 结构化输出

「抽取和判断都靠 LLM，但模型必须可换。我做了 provider 抽象层：`gate / extract / judge` + `Embedder` 两组 ABC，默认走一台 Windows 主机的 OpenAI-compatible 服务，config 一处切换，业务代码零改动。」

两个实打实的坑：
- **Qwen3 默认开 thinking**，JSON 外会混入思考文本导致解析失败。必须在 `extra_body` 传 `chat_template_kwargs.enable_thinking=false`。
- **结构化输出用 `response_format: json_schema`**，Schema 覆盖 Fact 全字段，解析失败重试一次；非法 fact 单条丢弃，不让整批失败。

「成本上我做两级门控：先用便宜规则过滤纯代码改动、闲聊，再交给 LLM 判断值不值得记；confidence < 0.7 直接丢。口诀是**便宜门控，贵在刀刃**。」

---

## 7:00–9:00 设计四：评测消融（量化每一步的增益）

「这类系统最容易『堆复杂度』——上向量、上图、上重排，但没人知道每一步值不值。所以我先建评测集，再做分阶段消融。」

- **评测集**：公开集（LongMemEval 等）证明方法 + 自建集贴个人场景。自建 24 题，其中 **10 条时效性样本**专门测「旧事实不该被召回」。
- **消融 Stage**：Stage0 仅 BM25 → Stage1 +向量 → Stage2 +图 → Stage3 +时效。指标 HitRate / Recall@K / MRR / 时效正确率 / 延迟。
- **图最后上**：Graphiti 依赖 LLM 抽实体边，成本和复杂度都高。我先跑通无图基线（BM25+向量+时效），再用评测量化图的边际增益——**证明不了增益就砍掉**。

「这也是我给自己定的纪律：**图最后上，增益可测。**」

---

## 9:00–10:00 踩坑、取舍与下一步

三个真实结论：
1. **Codex Stop hook 拿不到对话文本**——stdin 只有 `cwd` 等元信息。所以落盘兜底改成读最新会话文件（含 392 个 zstd 归档），这个结论我写在 `docs/hook-probe.md` 里。
2. **Graphiti 要 neo4j**，本地没服务。我按方案备选改成 networkx 自建双时态图，接口保持 `Index` 契约，后续能无痛替换——**接口先行，实现可换**。
3. **宿主接线做成分层**：WorkBuddy 走 MCP 注册，Codex 走 Stop hook，规则文件里写「涉及画像先调 recall」——按需检索，不强制每轮注入。

工程结果：**17 个任务、5 个波次、129 个测试全绿**，`record → recall → expand` 端到端跑通，5 个 MCP 工具可用。

下一步：接真实 vault 数据跑通 Stage0–3 消融表，把图增益量化出来；再评估 Cross-Encoder 重排是否值延迟成本。

## 附：可能被追问的问题

| 问题 | 回答要点 |
|---|---|
| 为什么用 Markdown 不用数据库做真源？ | 可读、可 git 审计、可迁移、无服务依赖；规模是个人万级，够用 |
| 多设备怎么同步？ | journal append-only + 视图 rebuild，冲突概率极低 |
| 抽取错了怎么办？ | fact 带 source 可追溯，supersede 而非删除，保留完整变更历史 |
| 为什么不每 session 注入 brief？ | 白吃 token 且可能 stale，改成 agent 按需调 recall |
| 向量检索失败怎么办？ | 融合层单路失败自动降级为 BM25，不拖垮整体 |
